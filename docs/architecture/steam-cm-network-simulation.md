# 玩家网络环境模拟与 CM 可用性验证

## 手动运行

```bash
./gradlew :steam-protocol:cmNetworkSimulation --configure-on-demand
```

默认每个场景使用 12 个固定种子，对旧策略/新策略分别运行。增加种子数：

```bash
./gradlew :steam-protocol:cmNetworkSimulation -PcmSimulationRounds=100 --configure-on-demand
```

无需设备、Steam 账号、代理权限或 root，不修改主机网络。
使用 `kotlinx-coroutines-test` 虚拟时钟，**保持生产 750ms/6s/30s/45s 超时不变**，
可以快速执行大量长超时场景。节点质量计时和健康记录时钟也注入同一个虚拟时钟。
固定种子决定抖动；旧策略与新策略从相同场景和种子开始。
两种策略的请求次序/数量不同，不能把它解释成逐包完全相同的实际网络回放。

默认输出到未跟踪的 `agent-tmp/`：

- `cm-network-simulation.csv`：场景、种子、策略、成功与否、虚拟耗时、连接总数、
  峰值 socket、登录次数、并行登录数、错误类型。
- `cm-network-simulation.csv.summary.txt`：各场景成功数、P50/P95（包含失败等待时间）。

普通 `:steam-protocol:test` 也执行该矩阵（每场景 3 个种子）和本地真实 transport 故障测试，
其模拟报告使用 `cm-network-simulation-unit.csv`，不覆盖手动完整矩阵报告；
`cmNetworkSimulation` 任务始终重跑。真实互联网 A/B 仍是另一个任务：

```bash
./gradlew :steam-protocol:cmSelectionBenchmark --configure-on-demand
```

## 场景和断言

| 场景 | 注入方式 | 新策略预期 |
| --- | --- | --- |
| 正常 Wi-Fi | 80ms 握手 + 80ms 登录 | 成功，无额外测速等待 |
| 高延迟移动网络 | 1100ms 握手 + 0–499ms 抖动 | 成功，不因快速窗口反复重建 |
| 类卫星慢网络 | 3500ms 握手 + 0–799ms 抖动 + 2000ms 登录 | 成功，保留原慢连接 |
| 前两节点黑洞 | 不触发任何 handshake 回调 | 跳过黑洞并成功 |
| 仅第 20 个节点可达 | 前 19 个全部黑洞 | 在 45s 内找到末尾节点 |
| 部分 IPv6 路由故障形态 | 前三个节点连接 reset，后续可达 | 成功切到其他节点 |
| 部分 DNS 污染 | 部分节点 UnknownHostException | 其他可达节点成功 |
| 部分 TLS 拦截 | 部分节点 SSLHandshakeException | 其他合法节点成功，不放宽 TLS |
| 间歇掉包与抖动 | 每节点每三次连接的第一次 reset | 仍能找到/重试可达路径 |
| 首次登录响应丢失 | 丢弃第一个 ClientLogon 响应 | 有限登录重试成功 |
| 前两节点登录路由不可用 | 握手成功，但登录返回 EResult 20 | 串行切换后成功 |
| DNS 全不可用 | 所有节点 DNS 故障 | 有界失败，不假装成功 |
| TLS 全不可信 | 所有节点证书失败 | 有界失败，不绕过证书校验 |
| WSS 全封锁 | 所有节点黑洞 | 不超过 45s，清理全部连接 |
| 认证门户 | HTTP 200 而非 Upgrade 101 | 明确失败，不当作连通 |
| Steam 限流 | 登录 EResult 84 | 仅一次登录，不换节点绕过 |
| 凭据失效 | 登录 EResult 5 | 仅一次登录，不归咎于节点 |

每个样本都验证：退出后活动 socket/登录数为零、并行登录不超过 1、
登录请求不超过 3 次、峰值 socket 不超过 4、新策略耗时不超过 45 秒。
对健康及高延迟可用场景，还断言新策略耗时不超过同种子旧策略 +150ms，作为回归门禁。

独立测试还覆盖：Wi-Fi 切到移动网络后不复用旧网络优选记录；旧连接迟到的失败回调
不破坏新会话；已有的注销/取消测试确保退出登录后不能重连旧凭据。

## 两层验证，而不是只伪造回调

`SteamCmNetworkSimulationTest` 通过可控 WebSocket 工厂模拟网络时序，
实际使用生产选择器、登录报文编解码器、失败切换和超时流程，注入的账号只是合成字符串。

`SteamCmTransportFaultTest` 使用真实 OkHttp + 本机 MockWebServer 验证：

- 自定义 DNS 抛出 UnknownHostException 后，有界失败。
- 本地 HTTP 200 认证门户无法通过 WebSocket 握手。
- 自签名但未被信任的 TLS 证书实际被拒绝，服务器收到零个 HTTP 请求。

测试证书只属于 localhost fixture，不加入生产信任列表。**不能为了可用性关闭证书验证。**

## 模拟发现并修复的行为

1. 原先最多探测/尝试 8 个候选，漏掉“只有目录末尾节点可达”。扩大到默认目录返回的
   20 个候选，同时维持 3 路 probe、3 次登录和 45s 总预算。
2. 原先 750ms 快路径结束就取消连接，高延迟可用网络会重复握手，甚至接近耗时翻倍。
   改为保留原连接，与后台 probes 竞争，**只竞争连接，不竞争账号登录**。
3. 原先每个失败候选都累加登录退避，全 DNS/TLS 故障会拖到总超时。
   改为只有实际登录失败才触发登录退避，明确的连接故障直接切换。

## 能说明和不能说明什么

- 这是**故障形态模型**，不是真实运营商、地区或 VPN 的精确复刻；不能推断全国覆盖率。
- “IPv6 故障”场景模拟某些路径 reset，不测试真实双栈 DNS 地址竞争或 NAT64。
- “丢包”模拟连接失败/响应丢失，不是 Linux `tc netem` 的逐包 TCP 丢包和拥塞模型。
- 没有验证目录 API 故障回退、下载带宽、长时间待机/NAT 回收、真实 VPN 分流，
  也没有验证 Cloud 业务 RPC、真实账号登录成功率。模拟从已有目录列表开始。
- 6 秒内连不上的所有路径仍可能失败；45 秒内无法发现的路径也没有可用性承诺。
- 没有外网、全部出口封锁、认证门户未登录、Steam 故障/限流或凭据失效，不能靠节点优选解决。

下一步真实设备验收应在不同运营商/Wi-Fi/VPN/IPv6 网络上运行 transport A/B，
再在用户明确授权下单独验证登录和只读业务 RPC，并记录成功率和 P95。
不要用模拟的虚拟毫秒作为真实用户提速宣传。

## 本次结果（2026-10-16）

17 个场景 × 100 种子 × 2 种策略 = **3400 次模拟**。
新策略在 11 个预期可恢复场景中全部成功（1100/1100），
其余 6 类全不可达/凭据/限流场景全部按预期失败，没有伪报成功。

| 场景 | 旧策略成功数 | 新策略成功数 | 旧 / 新 P50（虚拟 ms） |
| --- | --- | --- | --- |
| 正常 Wi-Fi | 100/100 | 100/100 | 160 / 160 |
| 高延迟移动网络 | 100/100 | 100/100 | 2126 / 2126 |
| 类卫星慢网络 | 100/100 | 100/100 | 5873 / 5873 |
| 前两节点黑洞 | 0/100 | 100/100 | 45000（失败） / 1140 |
| 仅末尾节点可达 | 0/100 | 100/100 | 45000（失败） / 37140 |
| 部分 DNS 故障 | 100/100 | 100/100 | 1820 / 470 |
| 部分 TLS 故障 | 0/100 | 100/100 | 1740（失败） / 550 |
| 间歇连接丢失/抖动 | 0/100 | 100/100 | 2693（失败） / 3606 |

新策略并非在每种情况下都“更快”：间歇故障的成功耗时长于旧策略快速失败的耗时；
全 DNS/TLS 故障时也需要覆盖更多候选，失败耗时从 1740ms 增至 2240ms。
应先看成功率，再看耗时，不能把快速失败误当性能优势。
