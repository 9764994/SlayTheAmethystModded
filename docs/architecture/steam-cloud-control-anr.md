# Steam 云控制锁导致启动器 ANR（2026-10-16）

## 证据与归因

归因：启动器。两份 dev5 日志都显示主线程等待 `SteamCloudControlStore` 的跨进程排他文件锁，随后触发 5 秒输入分发超时：

- `sts-launcher-crash-process-exit-20261016-113633-418-io.stamethyst-pid50365.txt` 第 15–18、50–68 行：选择模组启动方案 → 刷新主页 → 读取云状态 → `FileChannel.lock()`。
- `sts-launcher-crash-process-exit-20261016-113807-033-io.stamethyst-pid57038.txt` 第 15–18、60–71 行：点击后台同步并启动 → 写入后台启动标记 → `FileChannel.lock()`。
- dev4 的 `092532-342` 报告实际退出时间为 10 月 15 日，仅有 signal 9，Android 未提供 trace；不能据此判定同因。

报告只包含启动器进程线程，不能确定另一进程当时的具体持锁栈。代码中该锁覆盖存档事务及恢复，包括递归复制与 fsync；等待它的 UI 读写没有延迟上限。没有证据指向模组、渲染驱动或 Java 异常，也不能仅凭这些报告认定是 CM 会话撤销直接导致。

## 修复边界

- 控制状态读取不获取进程内/跨进程写锁，也不在读取时执行迁移写盘；首次写入时在写锁内迁移。保持无缓存，以便跨进程读取最新快照。
- 普通写入以及存档事务的常规文件 apply/rollback 均以原子替换发布文件。不能先 unlink 控制文件，否则无锁读取可能误以为尚未迁移并返回默认开关。
- 控制更新和存档事务继续共享写锁；不以移除写互斥、吞掉错误、超时返回默认状态等方式牺牲存档一致性。
- 后台启动先在主线程预留启动状态（防重复点击），在 IO 线程持久化启动标记，再回主线程排队同步/启动游戏。写入失败不越过安全边界启动游戏。
- 设置的禁用同步开关在独立单线程执行器中按顺序写入，避免 UI 等待存档锁，也避免被普通设置执行器的网络操作阻塞。

## 回归验证

`SteamCloudControlStoreTest` 覆盖：持写锁期间仍能读取快照；未迁移读取不写盘；无进程缓存；并发读取在事务反复 apply/rollback 时始终读到完整旧或新状态。事务恢复及云同步引擎现有测试继续验证存档一致性。

真实设备上的 ANR 消失情况仍需使用修复后的构建，复测“云同步期间切换启动方案”和“后台同步并启动”。
